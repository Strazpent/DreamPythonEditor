1Run window. The default presentation. A modal window that opens on the first pump (about 300 ms in) exactly over the Dream output area, with its position and size, so during the run the output area itself shows the run. Short runs end before it appears; their echo and output appear together on the next painted frame. It is one of only two modal Dream windows; the other is Paused.
2State and location. Running 41 s · Run #22, then the line Python was on at the last pump with its source text and file, and the statement that is running, 7 of 12 (statement mode, RUN-27). During a native call nothing paints, so this is the last line seen, not a live trace.
3Progress. dream_editor.progress(i, n, msg), where i counts finished items. The window shows i / n, a rate and an ETA once it has 3 samples, and the message. n=None gives an indeterminate bar.
4Live run view. The run's echo and output, drained on every pump, so a printed line shows at the first pump after it (about 110 ms at 10 Hz for a script that prints between sleeps); lines printed before the window opens appear when it opens. Each statement's echo comes just before its output; the loop's echo folds after 6 lines. The wheel and scrollbar scroll it, here back to the loop's start; ↓ 1,236 new lines returns to follow mode. When the run ends the window closes and the output area under it shows the same block: still following at the bottom if the view was following, or, as here after the wheel, with the line you were reading at the same place on screen. The Output Log gets the output in batches through UE_LOG, without the echo.
5Undo record size. Read on every pump. At 50% of the undo buffer the window warns. At 100% Dream ends the transaction and labels the run partly undoable; Undo Last Run warns before reverting a partial record.
6Stop. Esc stops the run when this window (or no modal) is active and no menu is open; inside a script's own dialog Esc means Cancel. Shift+F5 and the Stop button always stop. A pure-Python loop ends within 250 ms.
7Viewports resume when the run ends. The engine is not ticked during a supervised run, so viewports do not render. The platform blocks input to every other window.
8The editor behind. It keeps the frame it last painted before the run started, undimmed, with Starting… on the Run button and the code area as it was, so the running line shows in the Location row, not in the code view. While the Run window is open only the modal, tooltips and notifications are drawn: nothing outside the Run window is drawn or clickable until the run ends, as its footer says.
9Dream in the Unreal status bar. It is painted only when the editor paints, so during a Run-window run it keeps its last painted text (Dream · Starting · Run #22) and cannot be clicked; the Run window is what shows. The Running pattern is live only in task mode and in Live (docked) Preview.
10Stopping…, then cancelled. ScriptCancelled (a KeyboardInterrupt subclass) is raised at the next bytecode boundary; with and finally still run. The block ends with where and how long after Stop it took effect. The outcome is cancelled.
11The honest native-call note. A native call that does not pump Slate freezes the UI and delays Stop. Afterwards the Run window and the output say how long the last native call took.
12Interrupt cleanup. While your handler for the Stop is running, Dream does not re-deliver. After 10 s of cleanup it offers Interrupt cleanup, which delivers Stop once more.
13Task mode. Task running keeps the editor interactive and viewports render. Each step is its own undo step, Dream: task #31. Stop is on this item, on the tab banner, and Shift+F5 in Dream. A step longer than 1 s is supervised like a run.
14Live (docked) — Preview. An opt-in profile: the tab paints a run banner and streams output in the output area, and an arrow in the code gutter marks the line of the last pump, while an input pre-processor blocks the rest of the editor. It becomes the default only after the extended G2 suite is green for 4 consecutive weeks.
